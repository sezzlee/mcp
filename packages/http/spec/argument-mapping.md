# Argument Mapping

> Status: **a normative candidate**, implemented by the TS composer and the NestJS/Express SDK. Object-valued query parameters are validated by `compose` against the `object-query-*` family in `argument-mapping/`.

An agent's flat JSON arguments convert deterministically into an HTTP request. Input: a request template (method, route, parameter declarations with `in: path|query|header` and, for an array-valued one, its serialization style, plus an optional body declaration) plus an argument object. Output: the path and query string, data headers, and an optional body — JSON unless the template declares another media type ([request-bodies.md](request-bodies.md)). Every SDK MUST produce **identical** output from the same input; the `argument-mapping/` fixtures in [conformance](../conformance) test exactly that.

## Template construction rules (at tool-production time, fail-fast)

- Argument names MUST be unique: parameter and body property names MUST NOT collide (including a path `id` plus a body `id` → error; the fix is a rename or an override). The synthetic body-root name (`body`) goes through the same check.
- `GET`/`HEAD` MUST NOT declare a body.
- A header-positioned parameter MUST NOT use an identity carrier name (`Authorization`, `Cookie`) — identity is never an argument. More generally, a parameter whose location and name equal one of the descriptor's `auth.carriers` MUST be rejected (`identity_carrier_parameter`); header names compare case-insensitively, as HTTP defines them, query and cookie names case-sensitively.
- Every path parameter MUST have a `{name}` placeholder in the route (route constraints such as `{id:int}` are stripped in the template), and every placeholder MUST have a parameter. A path parameter MAY be an array.
- **Styles per location.** A declared `style` MUST be one the parameter's location has a wire form for; any other is `unsupported_parameter_style`:

  | Location | Styles                                                  | Absent means |
  | -------- | ------------------------------------------------------- | ------------ |
  | `path`   | `simple`, `label`, `matrix`                             | `simple`     |
  | `query`  | `form`, `spaceDelimited`, `pipeDelimited`, `deepObject` | `form`       |
  | `header` | `simple`, `form`                                        | `form`       |
  | `cookie` | `form`, `cookie`                                        | `form`       |

  An unstyled header array keeps the `form` default and its explode rule below, which is what every descriptor written before `simple` existed meant; `simple` folds an array on `,` whatever `explode` says, as OpenAPI defines it. A cookie array MUST NOT declare `explode: true` (`unsupported_parameter_style`): it repeats the cookie name and a server keeps one of the repeats. A cookie parameter's name MUST be an RFC 6265 token (`invalid_cookie_name`) — it is written as is, never through the encoder. Objects stay query-only (below).

- **Array serialization style.** A parameter carries an optional `style` (`form`, `spaceDelimited`, `pipeDelimited`) and an optional `explode` boolean. An absent `style` means `form`; an absent `explode` **defaults per style, exactly as OpenAPI does** — `true` for `form`, `false` for every other style. So a descriptor that says nothing at all still produces the repeated key that every earlier implementation had, while `{"style": "pipeDelimited"}` alone produces `a|b` rather than an error. The defaults are OpenAPI's because the vocabulary is OpenAPI's: a descriptor assembled from an OpenAPI fragment must not mean something different here than it does there. `spaceDelimited` or `pipeDelimited` with an **explicit** `explode: true` still has no wire form and MUST be rejected at template-production time (`unsupported_array_style`).
- **Object serialization style.** A query parameter whose schema is an object MUST declare `style: "deepObject"` and MAY declare `objectNotation` — `bracket` (the default) or `dot`, the character the composer writes between the parameter name and a member name. `objectNotation` is written by the SDK that discovered the endpoint, for the backend in front of it; it is never something an agent sees or chooses. A second `style` value (`deepObjectDot`) was rejected: `deepObject` is OpenAPI's own name for bracket notation, and a descriptor assembled from an OpenAPI fragment must not mean something different here than it does there — the same reason the array defaults are OpenAPI's. `deepObject` with an **explicit** `explode: false` has no defined wire form in OpenAPI and MUST be rejected at template-production time (`unsupported_object_style`); so MUST an object outside `query`, an object schema that does not declare `deepObject`, and a `fill` on an object parameter. Members are **one level deep**: a member that is itself an object, an array of objects, or a schema carrying `$ref`/`$defs` MUST be rejected (`unsupported_object_nesting`), as MUST a member name containing `[`, `]` or `.`, or one consisting only of digits — the notation would re-read such a name as structure it does not mean (`qs` reads `filter[0]` as array index 0).
- A header-positioned array parameter MUST declare `explode: false`. A repeated header cannot be represented — the composed headers are a name-to-value map, so a second write would overwrite the first — and folding into one comma-separated value is what RFC 9110 §5.3 already prescribes. Otherwise: `header_parameter_array`.

## Composition algorithm (at call time, in order)

1. **Reject unknown fields:** an undeclared argument → an `unknown_argument` error whose message lists the permitted names. The allow-list is the parameter names plus the body fields plus the body-root argument, if any. Silent dropping is forbidden.
2. **Path:** every path parameter is required (`missing_path_parameter` when absent, and when an array is empty — it fills no segment); a type gate applies (a value not matching the template's type → `invalid_path_type` — otherwise the route constraint would turn the error into an opaque 404); the value is percent-encoded and substituted into the placeholder. The style decides the segment: `simple` writes the value, `label` writes `.` before it, `matrix` writes `;name=` before it. An array's elements are encoded one by one and joined by the style's delimiters, written raw: `simple` `1,2`; `label` `.1,2`, or `.1.2` with `explode: true`; `matrix` `;id=1,2`, or `;id=1;id=2` with `explode: true`. Encoding is **strict RFC 3986**: everything outside unreserved (`A-Z a-z 0-9 - . _ ~`) is encoded, including `!'()*` and the space (JS: `encodeURIComponent` alone is not enough — `!'()*` are encoded separately; fixture: `percent-encoding-rfc3986`). **Raw concatenation is forbidden** — `"5/../admin"` becomes one encoded segment, which makes traversal structurally impossible.
3. **Query:** absent → the key is not written at all; `null` → `null_not_allowed`; key and value are percent-encoded separately; parameters are written in declaration order, so the output string is deterministic. An array is written according to its declared style: with `explode: true` (the default for `form`) the key repeats in element order (`?tag=a&tag=b`); with `explode: false` (the default for every other style) the elements are percent-encoded individually and joined by the style's delimiter — `,` for `form`, `%20` for `spaceDelimited`, `|` for `pipeDelimited`. **The delimiter itself is written raw, never through the encoder**: encoders disagree on `,` (a strict RFC 3986 encoder escapes it, `encodeURIComponent` does not), so routing it through one would make the byte string depend on the encoder. An element that itself contains the delimiter is therefore encoded and stays one element (`["a,b","c"]` → `?tag=a%2Cb,c`). An **empty array writes no key at all**, in every style, so that it stays indistinguishable from an absent argument rather than producing a bare `?tag=`.

   An **object-valued** parameter writes one key per member supplied, in the order the template declares — the same declaration-order determinism the parameter list itself has, frozen at template-production time so the agent's own JSON key order cannot change the composed string (`object-query-writes-members-in-declaration-order`). Alphabetical order was rejected: it would desynchronize from the host's own type for no gain. A member key is the parameter name, the notation's structural character, and the member name, with the parameter name and the member name percent-encoded **separately** and **the `[`, `]` and `.` written raw, never through the encoder** — encoders escape `[` and `]`, so routing them through would emit `%5B` and change what the backend's parser reads, by the same reasoning as the array delimiter. A member's value goes through the full type gate and the full RFC 3986 pass (`object-query-encodes-bracket-in-member-value`). An **absent member writes no key**, an **empty object writes no key at all**, and an **empty array member writes no key** — the same indistinguishable-from-absent rule the empty array already has. A `null` member is `null_not_allowed`. An array-valued member repeats the whole key in element order (`object-query-array-member-repeats-key`); `deepObject` has no folded form, so a delimiter is never written. A member the template never declared is `unknown_argument` by the same no-silent-dropping rule as step 1, and the message names it in dotted form under both notations, because the agent sends JSON and a path in JSON is dotted whatever goes on the wire.

4. **Header:** a CR/LF/NUL in a value → `header_injection`; an array-valued header is joined by its declared delimiter and the check runs on the joined value; an empty array writes no header; data headers are applied AFTER identity carriers (a collision is already impossible thanks to the template rule).

   **Content-serialized parameters.** A parameter that declares `contentType` is written as that media type instead of by style, and MUST NOT also declare `style` or `explode` (`unsupported_parameter_content`). `application/json` accepts any JSON value and writes it as `JSON.stringify` does — no whitespace, members in the order received, only `"`, `\` and control characters escaped, non-ASCII characters written as themselves, numbers in canonical shortest form (exponent notation stays unpinned, as above); `text/plain` accepts a string and writes it as is. The text then goes through the location's own encoding: one percent-encoded segment in a path, one percent-encoded value in a query pair or a cookie, and the raw text in a header, where the CR/LF/NUL check still applies. `null` is `null_not_allowed`, as for every other slot.

   **Querystring.** A `querystring` parameter is the whole query string and is always content-serialized: JSON is percent-encoded as one value after the `?`; `application/x-www-form-urlencoded` writes one `key=value` pair per declared member, in declaration order, repeating the key for an array member, with the same strict encoding and the same undeclared-member rejection as an object query parameter. `text/plain` has no query-string form (`unsupported_parameter_content`). An operation declares at most one (`multiple_querystring`), and never one beside `query` parameters (`querystring_with_query`): OpenAPI defines no way to merge them.

   **allowReserved.** A query parameter that declares `allowReserved: true` writes the RFC 3986 reserved characters `:/?@!$'()*,;[]` raw; `&`, `=`, `#`, `+` and `%` stay encoded, because they would split the pair, end the query or read back as a space. An array element's own delimiter stays encoded too, so `["c,d"]` is still one element. `allowReserved` on any other location is `unsupported_parameter_style`.

   **Cookie:** every cookie parameter supplied is written as `name=value` into **one** `Cookie` header, the pairs joined by `; ` in declaration order — RFC 6265 §5.4 has the client send a single header, and the composed headers are a name-to-value map in which a second write would overwrite the first. Absent → no pair; `null` → `null_not_allowed`; an empty array → no pair; an array is joined on `,`. Under `form` the value is percent-encoded like a query value, which always yields cookie-octets; under `cookie` it is written as is, and a value that is not made of RFC 6265 cookie-octets is `invalid_cookie_value` (a filled one is `deferred_value_invalid`).

   A dispatcher that also forwards an identity carrier's `Cookie` joins the two carrier first; a composed cookie whose name the carrier already sends is `cookie_carrier_collision`, never an overwrite in either direction — the agent would otherwise replace the caller's credential, or lose its own value without an error. Fixtures pin the join through the `carrierCookies` input.

   Cookies come in three classes, and only one is the agent's. An **identity** cookie (`session_id`, `jwt`) is a carrier and never an argument. A **context** cookie (`lang`, `currency`, `tenant`) is an argument the host usually fills through [argument-curation.md](argument-curation.md) — `constant` in a single-language deployment, `deferred` from the caller's profile or `Accept-Language`, `omit` when the backend's default is right; some backends read the locale only from a cookie and answer in their default language without one. A **data** cookie (`view`, `sort_pref`) is the agent's. Hiding every cookie by default was rejected: it would put context cookies such as `lang` where not even the agent can reach them, and hiding one cookie is already a curation. So was lowering `in: cookie` to a `Cookie` header parameter, which would put identity and data in one slot.

5. **Body — two modes.** _Field mode_ (declared body fields): declared fields not bound to parameters are collected into a single JSON object. Field mode **always** produces a body: with no declared field supplied the object is empty, and `{}` goes on the wire. There is no path by which field mode omits the body, which is why a body that is itself optional is never flattened ([schema-conversion-rules.md](schema-conversion-rules.md) Table 6). _Root mode_ (when the template declares a body-root argument): that argument's value is **the entire body** — it may be an object, an array, a string, a number or a bool; if the argument is absent, no body is sent and the backend's model binder decides (the same discipline as `absent-query-omitted`). Root mode is therefore the only mode in which "send no body" and "send `{}`" are both expressible, and they are different requests. The two modes MUST NOT be declared together in one template (`conflicting_body_modes`). **`Content-Type` and `Content-Length` are written if and only if a body is sent** — that is, always in field mode, and in root mode only when the argument was supplied. For a JSON body `Content-Type` is `application/json; charset=utf-8`; a template may declare another media type, and [request-bodies.md](request-bodies.md) defines how each one is written.

## Curated arguments

An endpoint may declare that an argument is renamed or hidden. The allow-list then speaks agent
names, the wire name of every curated argument is refused whatever the body allows, and a hidden
argument's value is written to its wire slot through the same type gate and the same encoding as an
agent-supplied one. The rules, the two invoke-time error codes and the resolve-once discipline are
in [argument-curation.md](argument-curation.md).

## Value formatting

- Number and bool conversion is **always invariant** (`1.5` MUST NEVER become `1,5`) and is a **canonical shortest** serialization: leftover notation in the source text is not preserved (`1.50` → `"1.5"`; fixture: `number-canonical-form`). The rationale: in languages that work with the parsed value (JS) there is no source text, and the canonical form is the natural intersection of the two languages. Magnitudes requiring exponential notation are not yet fixture-pinned — an unpinned area.
- The type gate produces `invalid_type` in positions other than the path: when the argument object is not a JSON object, when a non-array value arrives for a parameter declared as an array, or when a scalar conversion fails. For the `integer` type: a fractional value, or one outside the safe integer range (|n| ≤ 2^53−1) → `invalid_type`; `1.0` is an integer → `"1"`. (The previous "64-bit" limit was not representable in JS; the rule was pulled back to the intersection.)
- Semantic validation (ranges, formats, business rules) is NOT the SDK's job — the backend's own validation runs; the SDK only performs safe composition.

## Known limits

- **Dot notation cannot escape a dot inside a member value.** `.` is unreserved in RFC 3986, so neither `encodeURIComponent` nor `Uri.EscapeDataString` escapes it, and `?filter.name=a.b` is indistinguishable from a deeper path to a binder that splits on every dot (`object-query-does-not-encode-dot-in-member-value`). Bracket notation has no counterpart problem: both encoders escape `[` and `]` inside a value.
- **Grouping is one level deep.** A member that is itself an object is refused rather than flattened into `filter[a][b]`, because OpenAPI leaves `deepObject`'s second level undefined and the two notations' second levels are not the same shape, so the corpus would need one `expected` per SDK.
- **Curation does not reach a member.** A grouped parameter is renamed as a whole; there is no per-member rename, and a `fill` on the group is refused. Supporting one would need a second, object-shaped type gate with nothing driving it.
- **An SDK does not verify that its own backend parses the notation it writes.** A hand-assembled descriptor can name a notation the process in front of it does not read. The NestJS SDK checks the one case it can see — Express's `query parser` — and nothing more.
- **Express does not parse brackets by default.** Express 5 sets `query parser` to `simple`, which delivers one literal key; the NestJS SDK writes `bracket` and reports fatal `query_parser_not_extended` when the setting is not `extended`. It surfaces on the first meta-tool call rather than at boot, because that SDK builds its catalog lazily.
- **ASP.NET does not parse brackets at all.** `filter[status]` satisfies the binder's prefix test, which closes its empty-prefix fallback, but matches no leaf key — so the DTO binds empty rather than failing. A descriptor for an ASP.NET backend therefore names `dot`, which is not a preference but the only form that binds.
