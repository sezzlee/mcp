# Rich values and native workbook evidence

This phase-4 evidence was collected on 2026-10-18. It combines an original XlsxWriter
workbook, a workbook generated by Microsoft's Open XML SDK example, and a controlled
rich-error mutation. A Python ZIP/XML verifier checks each expected chain without using the
MCP parser. The linked-data and rich-error workbooks also passed the SDK's
`OpenXmlValidator(FileFormatVersions.Microsoft365)` with zero errors.

These are generated fixtures with supplied caches. They were not opened or recalculated in
Excel, and schema validation does not prove Excel UI behavior. The distinction matters for
dynamic arrays, saved filters and linked values that normally refresh from a service.

are deliberately retained under the Excel package's `test/fixtures`, with explicit
[provenance and MIT notices](../../servers/excel-mcp/test/fixtures/rich-values.PROVENANCE.md).

Drawing-anchored images carry different metadata from an in-cell `_localImage` value.
The [MS-ODRAWXML decorative schema](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-odrawxml/6146d89f-9146-415b-99e2-39e694b5a980)
defines a `decorative` element in the 2017 drawing namespace with an optional Boolean `val`.
[XlsxWriter's drawing writer](https://github.com/jmcnamara/XlsxWriter/blob/main/xlsxwriter/drawing.py)
provides a separate producer reference. Its drawing extension must not be inferred from an
in-cell rich value's `CalcOrigin` field, or vice versa.

## Linked data: the verified shape

The upstream program was compiled in an isolated fixture directory and called on a new
workbook containing one empty sheet. The canonical exact-source result is
`linked-seattle-source-exact.xlsx`, 8,544 bytes, SHA-256
`537a61c16e9c09a33d405e5f828d0e17b9462a69396e42203cc77706e63c6a12`.
The SDK uses generated relationship IDs and archive metadata, so a later generation can have
a different byte digest while satisfying the same fixed XML oracle.

The directly referenced chain is:

1. `Linked!A1`: `t=e`, cached `#VALUE!`, `vm=1`.
2. The workbook's `sheetMetadata` relationship targets `/xl/metadata1.xml`.
3. The first value-metadata block has `rc t=1 v=0`; metadata type 1 is `XLRICHVALUE`.
4. Its future-metadata block 0 contains `rvb i=0`.
5. Rich value 0 has `s=0`; structure 0 has type `_linkedentity2` and the five pairs below.

| Key                | Key type | Exact saved value                      |
| ------------------ | -------- | -------------------------------------- |
| `%EntityServiceId` | `i`      | `536870912`                            |
| `_DisplayString`   | `s`      | `Seattle`                              |
| `%EntityId`        | `s`      | `5fbba6b8-85e1-4d41-9444-d9055436e473` |
| `%EntityCulture`   | `s`      | `en-US`                                |
| `_Icon`            | `s`      | `Map`                                  |

Both `vm` and the metadata type index are 1-based. Future-block, rich-value and structure
indices are 0-based. The metadata filename and relationship IDs are not constants. This
sample therefore checks a real alternative to the XlsxWriter `xl/metadata.xml` layout.

The package also contains `_linkedentity2core` at rich value 13, supporting property bags,
arrays and a web-image record. A1 directly references rich value 0. A cached-label implementation
does not imply recursive property expansion or full support for the other rich types.
The upstream population and descriptive text are historical example data, not current facts.
Two Bing image hyperlinks are stored as external relationships. Generation, validation and
the independent verifier did not fetch them; the workbook has no downloaded media parts.

The handoff's missing linked-data example is therefore resolved for this concrete cached-label
shape. Provider refresh, arbitrary entity field traversal, other providers' entity variants,
web-image retrieval and an Excel desktop/web round trip remain unverified.

## Rich-error variant

`rich-errors.xlsx` is an original controlled mutation of `rich-values.xlsx`, 11,688 bytes,
SHA-256 `9ee3db1974c3bebed188a0e098815806bae179a6b6dca0c453ea01c80b7cdaa1`.
It appends two metadata-backed errors without changing the original image or ordinary-error
records. Both use an explicitly chosen `#VALUE!` compatibility cache, and both pass the
Microsoft365 schema validator. This does not assert that every Excel version saves the same
fallback spelling.

| Cell      | `vm` | Metadata type     | Future block / rich value / structure | Exact typed fields                               | Expected error |
| --------- | ---- | ----------------- | ------------------------------------- | ------------------------------------------------ | -------------- |
| `Rich!E5` | 3    | 2 = `XLRICHVALUE` | 2 / 2 / 1, `_error`                   | `errorType:i=8`, `colOffset:i=0`, `rwOffset:i=2` | `#SPILL!`      |
| `Rich!E6` | 4    | 2 = `XLRICHVALUE` | 3 / 3 / 2, `_error`                   | `errorType:i=13`                                 | `#CALC!`       |

F5 and F6 separately store direct `t=e` caches `#SPILL!` and `#CALC!` with no `vm`.
They exercise direct-cache compatibility. They are not evidence for the metadata structure.
The independent verifier uses fixed literal expectations for every index, key type and value,
and confirms that E2:E4 and the original two image references are preserved.

## Reproduction and acceptance boundary

The external evidence directories used in this run are `rich-fixture` and `linked-fixture`
beside the checkout. They contain the original writers, fixed Python verifiers, SHA-256
manifests and validator reports. `linked-fixture/source` retains the pinned upstream source,
the full MIT notice, a small original empty-workbook/validation harness, and a NuGet lock.
The original sample entry point and all rich-value creation methods are unchanged.

The exact-source SDK run used the following command, with `DOTNET_CLI_HOME`, `NUGET_PACKAGES`
and the SDK installation all inside the external fixture directory:

```bash
env DOTNET_CLI_TELEMETRY_OPTOUT=1 DOTNET_CLI_HOME=/workspace/scratch/9419ca03a883/linked-fixture/dotnet-home NUGET_PACKAGES=/workspace/scratch/9419ca03a883/linked-fixture/nuget /workspace/scratch/9419ca03a883/linked-fixture/dotnet/dotnet run --no-restore --project /workspace/scratch/9419ca03a883/linked-fixture/source/RichData.csproj -- /workspace/scratch/9419ca03a883/linked-fixture/linked-seattle-source-exact.xlsx
python3 /workspace/scratch/9419ca03a883/linked-fixture/verify_linked.py /workspace/scratch/9419ca03a883/linked-fixture/linked-seattle-source-exact.xlsx
python3 /workspace/scratch/9419ca03a883/rich-fixture/verify_fixture.py
python3 /workspace/scratch/9419ca03a883/rich-fixture/create_rich_errors.py
python3 /workspace/scratch/9419ca03a883/rich-fixture/rich-errors/verify_rich_errors.py
```

The exact verified bytes are retained as base64 CI fixtures; they need no external corpus or
.NET installation. Their independent verifier also works directly from the committed snapshots:

```bash
python3 packages/lab/excel-lab/scripts/verify-rich-fixtures.py
```

Normal package tests do not depend on the generation machine's paths. Malformed, out-of-range,
unknown or externally targeted metadata must retain an explicit limitation/fallback. Rich
image and linked-value compatibility caches must not inflate ordinary formula-error counts.
Native elapsed values use seconds for arithmetic; native percentages remain fractions;
shared currency symbols retain their unresolved symbol label instead of a guessed country.

The original XlsxWriter workbook and the SDK workbook were independently inspected before
runtime support was added. Package-level test results are recorded separately in
[FINDINGS.md](FINDINGS.md); XML/schema verification alone is not reported as an MCP pass.
