# Writing the docs

Every page under `apps/docs` follows these rules. This file is for the people writing the site; it
is not published on it.

The reader is a developer who wants one thing working: an agent reading their spreadsheets, a
backend exposed as tools. They arrive with a goal, not a curriculum, so the site is organized by
goal and every page is short enough to finish.

## Three sections

Each product has three kinds of page:

| Section        | Answers                        | Shape                                                                      |
| -------------- | ------------------------------ | -------------------------------------------------------------------------- |
| **Quickstart** | "How do I get it working?"     | One page, about five minutes: install, connect a client, ask, see a result |
| **Recipes**    | "How do I do this one thing?"  | One goal per page: a sentence of context, the calls, their real output     |
| **Reference**  | "What exactly does it accept?" | Generated from the built server; looked up, not read                       |

Rationale has no section of its own. A "why" belongs next to the behavior it explains, inside a
collapsed `:::details` block on the recipe that meets it, so the reader who wants it opens it and
everyone else keeps going.

```text
src/content/
  products.json            <- product registry: id, label, goal, tagline (array order = display order)
  redirects.json           <- retired slugs, per product, to the page that replaced them
  excel-mcp/
    00-quickstart.md       <- the product's one quickstart
    recipes/
      01-answer-a-question-without-reading-every-row.md
    reference/             <- generated by scripts/gen-reference.mjs
```

Order comes from the number in the file name, the title from the first `#` line, and the slug from
the file name with the number prefix removed. The route is `/docs/<product>/<slug>`, so a slug only
has to be unique **within its product**. Renumbering never changes a slug. Renaming one does: add the
old slug to `redirects.json`, and the site answers it with a 301 to the new page.

The sidebar is generated by `src/lib/content.ts`, and the home page lists every recipe. A new
**page** is registered nowhere. A new **product** is one folder plus one `products.json` entry.
`pnpm --filter @sezzlee/docs validate` fails CI on every structural violation.

## Page conventions

- **Title is the goal.** A recipe title is what the reader wants to do, in the imperative:
  `Read a CSV export`, not `How to read a CSV export` or `CSV handling`. A question or a "How to"
  title fails `validate`.
- **The first paragraph is the summary.** It is the page's meta description and its line on the home
  page: one or two sentences that say what the reader gets.
- **Commands, then output.** An `sh` block followed directly by another block is a command and its
  output; the site labels the second block "Output". No prose between them.
- **Alternatives go in tabs.** Client configurations and other either-or blocks go inside `:::tabs`,
  each fenced block with a `title="…"`. Blocks with a `title` are never run by `run-examples`.
- **Detours fold away.** Rationale, troubleshooting and edge cases go in `:::details[Label]`. If the
  page reads correctly with every `details` block closed, it is right.
- **One path.** A quickstart has no "alternatively". Where the reader must choose (a client, a
  framework), the choice is a set of tabs and the rest of the page does not branch.

Only `:::tabs` and `:::details` exist; `validate` rejects any other directive.

## Rules

These are not "nice to have". Documentation rots when they are broken.

### 1. One page, one product line

A page covers one product line; its path says which. What the products share is the spec, not a
product, and shared narrative belongs in `packages/http/spec/`.

A product folder is named after the product's package or directory (`excel-mcp`, `xml-mcp`).
`http-catalog` is the deliberate exception: it names a capability spread over two SDKs rather than a
package.

### 2. Reference is generated, not written

Nothing that has a machine-readable source is written by hand. `packages/http/spec/schemas/*.schema.json`
is this repository's single source of truth; the rule that holds for type generation holds for
documentation too. A schema field copied by hand into a page is a lie within three months. Where no
generation pipeline exists yet, the page **links to the schema** and does not copy its field list.

For an MCP server product the pipeline exists: `scripts/gen-reference.mjs` writes its tools, error
codes and limits pages from the built server, and `validate` fails when they drift. The only
hand-written reference input is `reference/<product>.json`, one sentence per error code and limit,
checked against the source in both directions.

### 3. RFC 2119 keywords only in the spec

`MUST` / `SHOULD` / `MAY` appear only in `packages/http/spec/*.md`. Site pages link to the spec; they
do not restate it.

### 4. Every code example runs

An example comes from a real test file, from a conformance fixture, or from a command someone ran.
An invented example is a lie within three months, and it spends the reader's trust in one go.

On a server product's pages, "someone ran it" is `scripts/run-examples.mjs`: it runs each `sh` block
against the workspace build and compares the output with the block below it. Write the command,
leave the output block empty, and let `--write` fill it.

If an example that has not been run is published anyway, the page says so. It is never published
silently.

Output blocks holding sample data are **never translated or edited by hand**. If the sample's own
string is in the wrong language, fix the sample and regenerate the output, or disclose it on the
page. A measured JSON block in `reference/02-schema-conversion.md` once carried Turkish
`description` values for months.

### 5. Policy names do not leak

`packages/http/spec/visibility.md` invariant 3: policy names never reach the agent. The same holds
for the docs — examples use no real customer policy name, tenant name or endpoint path. DemoApi's
cast of `OrdersRead`, `BusinessHours` and `alice`/`bob`/`carol` exists for this.

### 6. Rationale lives next to what it constrains

There is no separate decision-record tree. A normative rule is in the spec, a measurement or an
invariant is in a guard comment, a package-level decision is in that package's README. A `details`
block may explain that rationale but must not be its only source.

## Language

- Site content and UI strings are **English** — the site is sezzlee's public face.
- `packages/http/spec/` is **English** — the site links to it as normative.
- There is no i18n layer, on purpose: one language, no drift.

The **Google developer documentation style guide** is the reference for prose. Short sentences;
the reader is in the middle of something.

## Checklist for a new page

1. Which product, and which section: quickstart, recipe or reference? A reference page is generated;
   do not write one.
2. Is the title the reader's goal, in the imperative?
3. Does the first paragraph say what the reader gets, in two sentences at most?
4. Did every code example run (`run-examples`)? If not, does the page say so?
5. Does the page still read correctly with every `details` block closed?
6. Is there a field list copied from a schema? Turn it into a link.
7. Did a slug change? Add the old one to `redirects.json`.
8. Does every internal link point at a page that exists? `validate` checks it.
